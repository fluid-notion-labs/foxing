# Foxing: High-Performance Filesystem Replication Daemon

`foxing` (formerly xfs-mirror) aspires to be a production-grade, eBPF-powered replication engine for Linux filesystems (XFS, Btrfs, F2FS, Ext4). It captures filesystem events in the kernel and replays them asynchronously on a target directory, providing near real-time mirroring with robust consistency guarantees.

**Version:** 0.1 - Alpha 

## Key Features

* **Kernel-Level Capture:** Uses `eBPF` (kprobes) to intercept writes, renames, and attribute changes (`chmod`, `chown`, `xattr`, `fallocate`) with minimal overhead.
* **Async I/O Engine:** Leverages `io_uring` for high-throughput, non-blocking I/O replication.
* **Delta-Aware I/O:** Performs "Smart Sync" using BPF offsets. Large files are updated in-place (Delta Update) while new files use atomic temp-rename strategies, drastically reducing I/O for database workloads.
* **Intelligent Auto-Tuning:** The `TargetTuner` creates a closed feedback loop using:
    * **Latency:** End-to-end event processing time.
    * **Backpressure:** Internal queue depth monitoring.
    * **System Health:** Governor stress signals.
* **System Governor:** A background monitor that tracks System Load Average. It proactively throttles low-priority tasks (hydration) and forces workers into "Conservative Mode" during high system stress to prevent source starvation.
* **MARS Versioning:** (Mirror & Archive Recovery System) Provides zero-cost `Reflink` snapshots on every `fsync` for atomic rollback capability.
* **Force Versioning:** Allows critical files (databases, WALs) to bypass system governors and retention limits, guaranteeing history preservation even under high load.
* **Resiliency:** Features persistent sidecar metadata, mandatory file locking, and automatic hydration on event loss or sequence gaps.

## Architecture

1.  **Source:** `mirror.bpf.c` intercepts VFS calls (`vfs_write`, `notify_change`, `vfs_fallocate`, etc.) and pushes them to a Ring Buffer. It explicitly filters out events generated by the daemon itself to prevent feedback loops.
2.  **Ingestion:** `bpf.rs` reads events, handles PID filtering verification, and dispatches them to sharded `EventQueues`.
3.  **Worker:** `worker.rs` implements a complex state machine:
    * **Coalescing:** Merges adjacent write operations to reduce IOPS.
    * **Smart I/O:** Decides between Atomic Write (safe but slow) vs. In-Place Delta (fast) based on file state.
    * **Metadata Replay:** Applies attributes (`setxattr`, `utimes`) read from the source.
4.  **Governor:** Background monitor checks system health and signals workers to back off during high load.

## Requirements

* **Kernel:** Linux 5.14+ (Required for modern `libbpf` and `io_uring` features).
* **Build Tools:** `cargo`, `clang`, `llvm`, `bpftool`, `libbpf-dev`.
* **Target Filesystem:** XFS or Btrfs recommended (for Reflink/CoW support).

## Configuration (`config.toml`)

See `config.toml.example` for detailed configuration scenarios including Gaming, Database, and Developer profiles.

```toml
# Minimal Example
worker_count = 4
queue_max = 200000

[[sources]]
path = "/mnt/data"

  [[sources.targets]]
  path = "/mnt/backup"
  profile = "SSD"
  enable_versioning = true
  max_versions = 5
  
  # Force critical files to keep 20 versions regardless of disk pressure
  force_versioning = false
  force_version_includes = [".*/critical_db/.*"]
  force_retention_count = 20
```

## Capacity Planning & Sizing

Unlike block-level replication, `foxing` incurs a per-file metadata cost on the target filesystem.

**The Metadata Tax:**
* **Optimized Metadata:** `foxing` now uses Native Extended Attributes (`user.foxing.*`) by default on supported filesystems (XFS, Btrfs, Ext4). This reduces the per-file overhead to **near zero** (0 extra inodes).
* **Legacy Fallback:** On filesystems without xattr support (FAT32, NFSv3), it falls back to creating `.foxing_meta` sidecar files, incurring a 4KB/1-inode tax per file.

**Recommendation:**
Always provision the Target volume with at least **5% more capacity** than the Source to accommodate Versioning history and potential filesystem overhead differences.

> **Critical:** If the Target fills up before the Source, the daemon enters a "Safe Stall". See **[Failure Scenarios: Story 5](docs/FAILURE_SCENARIOS.md)** for a detailed breakdown of how the system handles mismatched capacity and ENOSPC errors.

## CLI Usage

The daemon runs as a foreground process or systemd service.

```bash
# Start Daemon
foxing daemon --config /etc/foxing.toml

# Check Status (shows running version)
foxing status

# View Metrics (Text)
foxing metrics
```

### Versioning Commands (MARS)

If `enable_versioning` is active, the daemon creates zero-cost copies on `fsync`.

```bash
# List versions of a specific file
foxing version list /mnt/backup_drive/database.db

# Revert file to a specific epoch (atomic rollback via Reflink)
foxing version revert /mnt/backup_drive/database.db --epoch 105432

# Extract a past version to a new file
foxing version copy /mnt/backup_drive/database.db --epoch 105432 --destination /tmp/db_restore.db
```

## Safety Mechanisms

1.  **Loop Prevention:**
    * **Device Filtering:** eBPF explicitly ignores events on the Target device.
    * **PID Filtering:** eBPF explicitly ignores events generated by the daemon's own PID/TGID to prevent metadata feedback loops.
2.  **Partial Write Protection:**
    * **Atomic Mode:** New files are written to `.tmp.uuid` and renamed.
    * **Delta Mode:** Existing files use In-Place updates with MARS versioning acting as the safety net for crash consistency.
3.  **Consistency:**
    * `fsync` events on the source trigger a global barrier on the target.
    * Full metadata replication (`xattr`, `acl`, `timestamps`) ensures permission fidelity.
4.  **Global Emergency Pruning:**
    * If the Target filesystem hits `ENOSPC` (Disk Full), the system automatically deletes the oldest version snapshots from *any* file to free up space and allow the Live Mirror to continue.

```bash
### Why the name?
"Foxing" is an archival term referring to the brownish spots and rusty patina that appear on old paper, stamps, and photographs over time. Historically, it was also used to describe the desilvering or "rusting" of antique mirrors.

Since this project is a Mirror written in Rust, the name fit perfectly.

It also nods to the classic pangram, "The quick brown fox jumps over the lazy dog." In our case, this represents the core architectural goal: allowing the "Quick Fox" (your fast NVMe Source drive) to perform at full speed, completely decoupled from and leaping over the latency of the "Lazy Dog" (your slower backup HDD/Network Target).
```
