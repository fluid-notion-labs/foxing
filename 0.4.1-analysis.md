# Synthesis: dcp-factor IVI Pruning x foxingd CQRS Event Dispatch

## 1. dcp-factor IVI Algorithm — Core Innovation

The IVI (Integer Vector Inversion) algorithm solves integer factorization through a **frontier-based breadth-first search** with **multi-layered feasibility pruning**. The key insight applicable to foxing:

### 1.1 Frontier Expansion with Early Pruning

The algorithm maintains a **frontier** of candidate states. At each step, it expands candidates then **prunes infeasible branches** before the frontier grows. Nine pruning rules applied in **fail-fast order** (cheapest first):

1. **Symmetry elimination** (P <= Q) — halves search space
2. **Exact termination** — validates final state
3. **Immediate overshoot** — product already exceeds N
4. **Sqrt-based hard bound** — single arithmetic comparison
5. **Growth envelope** — bounds maximum future contribution
6. **Minimum contribution** — bounds minimum future contribution
7. **Linear-term gap feasibility** — mid-depth tightening
8. **Upper tail tightening** — division-based coupling
9. **Length split feasibility** — digit count constraint

**Key property:** O(n) complexity because frontier width is bounded (~50 states max per position).

### 1.2 Mapping to foxingd

| IVI Concept | foxingd Equivalent |
|------------|-------------------|
| Frontier of candidate states | Coalescer EventBatch |
| Digit pair expansion | eBPF event ingestion |
| Feasibility pruning | Transient lifecycle pruning + coalescing |
| Fail-fast ordered checks | Event classification (control vs data plane) |
| Growth envelope bounds | BBR tuner batch size limits |
| Symmetry elimination | Inode-based event deduplication |

## 2. Current foxingd CQRS Architecture

### 2.1 Event Flow
```
eBPF kprobes -> Ring Buffer -> BPF Processor -> ReorderBuffer -> EventQueue -> Workers
                                                                     |
                                              Fanout (hash by parent_inode)
                                                       |
                                       Worker 0 (Control)  Workers 1-N (Data)
                                            |                    |
                                       Coalescer              Coalescer
                                            |                    |
                                       SmartCopier            SmartCopier
```

### 2.2 Event Dispatch (event.rs)
- **Control plane** (Rename, Mkdir, Unlink) -> Worker 0 (serialized)
- **Data plane** (Write, WriteRange) -> hash(parent_inode) % (workers-1) + 1
- Static partitioning — no load-aware rebalancing

### 2.3 Columnar Layout (columnar.rs)
EventBatch uses struct-of-arrays: separate Vec for inodes, types, offsets, lengths.
Cache-efficient for scanning but SIMD not exploited.

### 2.4 Coalescing (ordering.rs)
- Head-of-batch scan with configurable scan_depth
- Elastic depth (10x at >80% utilization)
- Transient lifecycle pruning (create->unlink chains)

## 3. Problems Identified via VM Testing

### 3.1 Event Worker CPU Spin (CRITICAL — P0)
`std::future::ready(retry_queue.pop_ready())` creates immediately-resolving future.
4 tokio threads at 88% CPU each with zero events. Starves hydration workers.

### 3.2 Static Fanout Hotspots
One directory with 10K files -> one worker overwhelmed.
No rebalancing, no XFS AG awareness.

### 3.3 Columnar SIMD Opportunity
Linear inode scan in coalescer — AVX2/NEON could give 4-8x speedup.

### 3.4 No XFS Allocation Group Awareness
XFS AGs are independent lock domains. AG-aware worker mapping would eliminate contention.

## 4. Proposed Optimizations (IVI-Inspired)

### 4.1 Fail-Fast Event Pruning (move pruning earlier)
Apply before fanout, not after:
1. Internal traffic filter (existing)
2. Stale generation check (new)
3. Transient lifecycle detection (move from coalescer to BPF processor)
4. AG-based partitioning (new — XFS only)
5. Write coalescing at ingestion (move from worker to BPF processor)

### 4.2 XFS AG Worker Mapping
`AG = inode / inodes_per_ag` via XFS_IOC_FSGEOMETRY.
Each worker owns one AG's lock domain — zero contention.

### 4.3 SIMD Columnar Scan
AVX2: 4 u64 per iteration for inode matching in coalescer.
NEON: 2 u64 per iteration.

### 4.4 Worker Select Fix (P0)
Replace `std::future::ready()` with timer-guarded branch.
Eliminates 350% idle CPU.

### 4.5 Bounded Frontier Width
IVI's ~50 state bound -> coalescer: if >10K events, aggressive full-batch coalesce.

## Core Decoupling Mechanics Explained

### 1. Handling the "Metadata Storm" (The Shortcut)
When a user extracts a massive archive or compiles a project, the source CPU/NVMe combo generates hundreds of thousands of `Create`, `Write`, and `Rename` events per second. 
* **Without Foxing:** A standard mirror would freeze the NVMe drive, waiting for the target to execute 100,000 tiny metadata operations.
* **With Foxing:** The Elastic Coalescer absorbs the events. By analyzing the "Adjacent Possible" state of the filesystem (via look-ahead depth $m$), Foxing annihilates redundant event chains (e.g., temporary compiler objects). The target only executes the final, net-effective state.

### 2. Handling the "Catastrophic Stall" (The Leash Cut)
If the target HDD spins down, the SD Card does garbage collection, or an NFS share drops packets, target throughput effectively hits 0 MB/s.
* **Without Foxing:** The userspace queues fill up. The kernel `vfs_write` hook blocks, freezing the entire source operating system until the target recovers.
* **With Foxing:** `bpf_ringbuf_reserve` triggers a controlled failure. The BPF program gracefully abandons the event to preserve source uptime but strictly updates the `local_seq_map`. The source OS is completely unaffected. Once the target wakes up, Foxing detects the sequence gap and patches the missing files via the bounded Frontier Hydration engine.

### 3. Handling Extreme Hardware Asymmetry (The Offload)
In high-end servers, copying data between two NVMe drives using standard `read()` / `write()` syscalls consumes massive CPU cycles due to context switching and memory bus saturation.
* **Without Foxing:** CPU hits 100% `sys` time.
* **With Foxing:** By delegating the transfer to `io_uring` with `splice` or `FICLONE` (Reflink), the data movement happens entirely within the kernel or storage controller. Userspace RAM is untouched, leaving the CPU free for actual application workloads.
